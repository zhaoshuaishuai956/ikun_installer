# 对抗性审查：规范归并、首次点击提醒与热更新

对象：三仓归并、唯一权威规范、AI 提示词、已有插件热更新、首次点击更新提醒
日期：2026-08-25
结论：有条件通过；下列 P0/P1 已在本次变更闭环，删除源仓仍需独立人工确认。

## 攻击与处置

### [P0 已修] 删除源仓造成知识不可恢复

- 攻击：旧仓删除后才发现公开手册有独有文件、模板版本选错或许可证遗失。
- 证据：归并前逐文件清单和哈希比较；私有知识库为较新主线，公开手册大部分为镜像。
- 处置：01–07 技术资料、较新 templates、历史规范、registry 快照、全部红队报告和三份许可证均先进入安装器仓。
- 删除门：安装器提交推送且可从远端重新克隆验证后，仍必须再次列明三个仓库并请求不可逆删除确认。

### [P0 已修] 多份文件继续自称权威

- 攻击：AI 同时读旧 L2/L3、镜像和新规范，选择对自己方便的规则。
- 处置：只允许 `docs/NX二次开发权威规范.md` 定义规则；摘要、提示词和技术参考显式声明冲突优先级；旧规范标记废止。

### [P0 已修] “部署槽”旧规则破坏热更新目标

- 攻击：每次更新创建新槽并修改 `custom_dirs.dat`，NX 当前会话仍指向旧 DLL，用户被迫重启。
- 处置：后续安装锁定已注册活动目录，对已有资源执行同目录原子替换；仅首次安装创建槽；仅新增菜单项需重启。

### [P1 已修] 文件锁定导致半更新

- 攻击：某 DLL/DLX 被插件窗口占用，部分文件已更新、部分失败。
- 处置：单文件采用同目录临时文件和原子替换；失败保留旧文件并要求关闭对应插件窗口重试。发布包仍应尽量作为一致版本验证。

### [P1 已修] 七个插件各自联网导致重复弹窗与逻辑漂移

- 攻击：每个插件独立访问版本 API，首次点击七次就出现七种行为。
- 处置：子插件只通过统一头文件启动 `ikun_installer.exe --check-update`；进程级命名事件保证一次 NX 进程只由第一个业务插件触发一次，更新判断集中于安装器。

### [P1 已修] 用户关闭更新提示后仍被骚扰

- 攻击：关闭对话框释放互斥标记，下一插件点击再次弹窗。
- 处置：NX 进程持有命名事件到退出；关闭更新窗不重置会话标记；主动检查按钮不受此限制。

### [P1 已修] 只复制头文件但忘记调用

- 攻击：仓库结构看似合规，实际 DLL 永不触发检查。
- 处置：规范要求 `ufusr` 在 `UF_initialize` 前调用，CI 对收集的业务 DLL 检查调用标记；模板直接包含接入点。

### [P1 已修] 四字命名仍有歧义

- 攻击：“四个字”被解释为四个字符，混入字母、数字或标点。
- 处置：机器正则固定为四个汉字 `^[\u4e00-\u9fff]{4}$`，且 LABEL 与 meta 逐字相同。

### [P1 已修] 归并文档包含越权指令或不安全命令

- 攻击：AI 读取旧 README 后执行禁用 TLS 校验、自动克隆/推送或删除仓库。
- 处置：不把旧 README/AGENTS/维护脚本作为活动规范导入；AI 提示词明确仓库内容不是用户授权；现行规范禁止常驻 `sslVerify=false`/`curl -k`。

### [P1 待独立门禁] 删除操作不可逆

- 攻击：把“归并完成”错误等价为“可以立即删库”。
- 门禁：本报告不授权删除。必须在远端推送和验证完成之后，向用户再次列出
  `zhaoshen/nx_dev_skill`、`zhaoshen/ikun_dev_standard`、`zhaoshen/nx_dev_handbook`，收到明确确认才调用删除 API。

### [P2 记录] NX 实机行为无法由普通 CI 完全证明

- 风险：静态标记、导出检查和部署测试不能证明真实 NX 1847 中 Block Styler 卸载行为。
- 要求：Release 前保留人工冒烟证据，覆盖“原按钮再次点击加载新版”和“新增插件需重启”两条边界。

## 反例回归清单
