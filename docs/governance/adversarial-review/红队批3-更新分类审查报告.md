# 红队批 3：插件资源与安装器更新分类审查

## 结论

原机制把 Gitea Release 名称的递增版本同时当作插件资源版本和安装器本体版本。CI 每次收集子插件都会重新打包 exe，导致 NX 即使只发现一个 DLL/DLX 变化，也提示下载约 110 MB 的完整安装器，破坏“资源优先、原子热更新”的产品语义。

本批改造将两个版本拆开：资源清单记录 `release_version`、`installer_version` 和 `update_kind`。客户端继续逐项校验并原子替换资源，但完整安装器提示只比较 `installer_version` 与本地程序集版本。

## 对抗性检查

| 反例 | 旧行为 | 现在的判据/处置 |
|---|---|---|
| 子插件 DLL/DLX 更新，安装器源码不变 | 误报完整安装器更新 | `update_kind=plugins`，沿用上一次 `installer_version`，只下载变化资源 |
| 仅更新 `plugins.json`、菜单或图标 | 误报完整安装器更新 | 归入资源发布；新增插件仍由资源结果提示重启 NX |
| 安装器运行时代码或依赖变化 | 可能只热更新插件，漏掉安装器修复 | 分类脚本将运行时代码/项目依赖标为 `installer`，提升 `installer_version` |
| 每次 CI 注入 `<Version>` 或修改 CHANGELOG | 把构建编号当本体版本 | 分类脚本忽略版本行、文档、测试和 CI 文件 |
| 历史 Release 没有分类元数据 | 新客户端无法知道本体版本 | 回退历史 Release 名称版本，兼容迁移；之后正文写入不可见版本标记 |
| Release 清单伪造未知分类 | 客户端执行未定义分支 | `ResourceManifest.Parse` 只接受 `plugins` / `installer`，未知值拒绝 |
| 资源版本高但安装器版本不高 | 仍提示完整安装器 | 两阶段判断：资源先更新；本体版本不高则直接结束 |

## 证据

- `ci/classify-update.sh`：按 Release 上次目标提交分类，版本行不构成本体变化。
- `ci/test-update-classification.sh`：覆盖插件专属变化和安装器运行时代码变化。
- `ResourceManifest.Parse`：校验本体版本格式和更新类型白名单。
- `UpdateManager.IsInstallerUpdateAvailable`：完整安装器提示只比较安装器本体版本。
