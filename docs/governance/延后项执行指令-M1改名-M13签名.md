## M13 · 安装器代码签名 + 更新器 fail-closed（规范 §9.3.3，优先级 P0）

### 背景
现状：`VerifyDownloadedInstaller` 对无签名 exe 放行（信任边界 = Gitea + TLS）。M13 落地后：
签名缺失或无效 → **拒绝执行**。切换必须原子：首个已签名 exe 与 fail-closed 校验同一版本发布。

### 步骤
1. **取得代码签名证书**（二选一）：
   - 企业内网 CA（推荐）：申请 Authenticode 证书（代码签名 EKU），私钥**不落 CI**，放开发机/HSM
   - 商业证书（如 Sectigo/GlobalSign Code Signing，约 ¥1000+/年）
2. **本地签名脚本** `scripts/sign.ps1`（新增到 ikun_installer，不入 CI）：
   ```powershell
   # 用法: pwsh scripts/sign.ps1 -Exe <path> -CertThumbprint <thumbprint> [-TimestampUrl http://timestamp.digicert.com]
   param([string]$Exe,[string]$CertThumbprint,[string]$TimestampUrl)
   $cert = Get-ChildItem Cert:\CurrentUser\My | Where-Object Thumbprint -eq $CertThumbprint
   Set-AuthenticodeSignature -FilePath $Exe -Certificate $cert -TimestampServer $TimestampUrl
   ```
3. **发布流程**（改动 pack.yml 或改为「CI 出包 → 开发机签名 → 回传发布」）：
   - 方案 A（推荐，CI 不改）：CI 只出包不发布；开发机下载 exe → 签名 → 手工/脚本更新 Release（资产+sha256）
   - 方案 B：CI 内签名需私钥进 CI（**禁止**，违背规范 §11/M13）
4. **更新器 fail-closed 切换**（与首个签名版同一提交）：
   - `UpdateManager.VerifyDownloadedInstaller`：`sig == false`（无签名）分支从「放行」改为 `return false`
   - 同步更新 `tests/Program.cs` 的「无签名处置」用例断言
   - 本地 `dotnet build` + `dotnet run --project tests` 全绿后提交
5. **验证**：无签名 exe 被更新器拒绝；签名 exe 正常安装；Release 正文 sha256 与文件一致

### 验证
- 下载无签名 exe → 更新器显示拒绝且不 runas
- `Get-AuthenticodeSignature` 显示 Valid + 时间戳
- 发布一个签名里程碑 Release，用户侧实测更新成功
