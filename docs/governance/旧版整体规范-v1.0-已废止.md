## 0. 为什么需要这份规范（基于 2026-08 现状盘点）

盘点发现的事实（详见附录 A）：

| # | 现象 | 危害 |
|---|------|------|
| 1 | 插件事实有 4 处并存且互相漂移：`plugins.json`、`plugin.meta`、`08` 附录表、`DeployResources/startup` 菜单。附录表写 `text_auto_layout`「否」但 `plugins.json` 已收录；`plate_dwg_export` 同理；`runner_section_area` 到处未登记 | 新人/新 AI 会话无法判断「谁说了算」 |
| 2 | 11 个插件中 9 个没有 `CHANGELOG.md`（并入爱坤的 7 个里 5 个缺失：block_boss_layout、ejector_layout、pmi_hole_dim、single_line_text、text_auto_layout）；`MultiEntityNester` 用永不冻结的 `Unreleased` 段；`single_line_text` 用 `开发文档.md` 代替 | 发布说明退化为 commit 标题，用户看不懂「这次更新了什么」 |
| 3 | 制品二进制（dll/dlx）直接提交进 git，CI 只收集不编译；打包闸门只有「发布说明回归测试」 | 无法机器验证「这个 dll 是不是这份源码编译的」；`runner_section_area` 甚至把 `.obj` 提交入库 |
| 4 | `MultiEntityNester` 驼峰命名不合规但长期未改；改名成本没有可执行的分解方案 | 命名债无限拖延，新插件有样学样 |
| 5 | `ikun_installer` 仓库提交了 5 个插件的旧二进制（`DeployResources/application/`），CI 每次 `rm -rf` 重建；本地 `build.ps1` 用它们 + 硬编码 `E:\NX二次开发\项目`、`Y:\...\爱坤工具箱` | 本地构建结果与 CI 不一致；换机器即失效 |
| 6 | `custom.men`/`.rtb`/`.tbr` 是 GBK 编码，其余文件全 UTF-8，无任何机器守卫 | 一个编辑器「顺手存成 UTF-8」就让 NX 菜单变乱码且无人知晓 |
| 7 | 版本模型混乱：`latest` 滚动 Release（v2.1.0.54）与冻结的里程碑 Release（v2.1.0）并存且无规则说明；插件自身无版本字段 | 「用户装的到底是哪版」说不清 |
| 8 | 无分支保护、无 PR/审查流程、提交未签名；`notify-installer.yml` 每仓复制一份且持有同一 dispatch token | 单人项目尚可，多代理协作时无法防事故 |
| 9 | 分支命名分裂：插件仓全 `master`，两个知识库仓是 `main` | 脚本/约定写死 `master` 时对知识库失效 |
| 10 | `update.ps1`（本机旧式同步）与 `UpdateManager`/`ikun_updater`（Release 更新链）两套更新逻辑并存 | 用户按哪个更新说不清，逻辑分叉 |
| 11 | 更新链信任边界弱：安装器无代码签名且更新器「无签名=放行」；`INSTALLER_DISPATCH_TOKEN` 实为跨仓读+release 写的万能 PAT 在 7 仓复制；`icon_cn` 等 meta 字段可注入 ImageMagick | 更新链被替换=全员管理员代码执行；token 泄露=覆盖 `latest`；凭证可经公开图标外泄 |

规范的目标：**让以上每一条都有一条机器可判或人可执行的规则去收敛它**，并让规则本身可被对抗性审查持续检验。

## 1. 第一性原理推导

### 1.1 爱坤生态不可再分的目的（What is this FOR）

爱坤生态的存在目的只有一条：**让 NX 用户持续用上「这批自研插件」的最新、正确版本，且成本不随插件数量增长而失控。**

把它拆成 5 个原子价值（缺任何一个，整个生态都在慢性失效）：

| 原子价值 | 定义 | 反例（现状） |
|---|---|---|
| **V1 可用** | 每个插件在 NX 里能看到、能加载、点了能干活 | 图标缺失的插件菜单白块；GBK 被改乱码 |
| **V2 可达** | 新版本能从开发者到用户，且用户知道「新在哪」 | 无 CHANGELOG 的插件更新只有 commit 标题 |
| **V3 可追溯** | 任一用户手上的二进制，能回溯到「哪份源码 + 哪次构建 + 什么说明」 | 直接提交的 dll 与源码无绑定证据 |
| **V4 可演进** | 加插件、改插件有确定性路径，不需要「会的人在场」 | 接入步骤散落在 4 个仓库 5 份文档 |
| **V5 不失控** | 流程成本是 O(插件数)，不是 O(插件数²)；规则随规模自动执行 | 每加一个插件要手工改 4 处且无人校验 |

### 1.2 由目的推出的设计原则

| 原则 | 内容 | 治的现状条目 |
|---|---|---|
| **P1 身份唯一** | 一个插件只有一套名字：仓库名 = 本地目录 = dll 基名 = 插件 id（四同）。中文名两级由 `plugin.meta` 唯一定义 | #4 |
| **P2 单一可信源（SSOT）** | 每一类信息只有一个权威定义点，其余全部派生或校验，见 §4.1 矩阵 | #1 |
| **P3 制品可追溯** | 任何上架制品必须能机器回溯到源码提交 + 构建记录 + 变更说明；做不到就拒绝打包 | #3 |
| **P4 版本单一权威** | 版本号只有一处定义：安装器在 csproj，插件在 CHANGELOG 段头。发布轨道规则显式化 | #7 |
| **P5 机器判据优先** | 一切关卡优先用「机器可判定」的判据（退出码、dumpbin、XML 校验、CI gate）；人工只做机器做不了的判断 | #6 |
| **P6 约束显式化** | 历史包袱（GBK 菜单、扁平部署、无法容器编译 NX 插件、rolling latest）必须写成显式约束清单，改前不许静默破坏 | #5 #6 |
| **P7 渐进收紧** | 新规则从「警告」起步，观察一个周期后升级为「闸门」；避免规范第一天就逼死正常开发 | 全部 |
| **P8 对抗审查制度化** | 规范修订、重大架构变更、发布制品、新插件接入，四类动作必须经过独立红队攻击，P0 级发现未闭环不得合并/发布 | 用户点名要求，见 §13 |
| **P9 自动化优先于记忆** | 能写成脚本/CI 的规则绝不依赖「记得住」；记忆只在机器边界之外兜底 | #5 #6 |

### 2.2 规范分层与权威链

```
L1  gitea-for-ai           AI 代理的 Git/Gitea 工作流（提交格式、凭证、错误恢复）—— 任何仓通用
L2  nx_dev_skill            NX 插件开发知识 + 05 执行协议 + 08 子项目开发规范（单仓工程标准）
L3  本文档（ikun 整体规范） 生态协同：身份/SSOT/版本/制品/发布/接入/治理/对抗审查 —— 最高优先
```

规则：
1. **冲突时 L3 > L2 > L1**；L3 不重复定义 L1/L2 已有的内容，只引用。
2. **本文档存放点**：定稿后以公开仓 `ikun_dev_standard`（新建）或 `ikun_installer/docs/ikun-整体开发规范.md`
   为存放点（维护者二选一并登记在本文件头部）；附录 A 清册与镜像链均以该文件为源头。
3. **镜像链单向（M8 完成起生效）**：`L3（本文，权威）→ nx_dev_skill/08-子项目开发规范.md（镜像）→ ikun_installer/docs/子项目开发规范.md（镜像）`。
   **过渡期（M8 之前）**：08 仍自称权威（其头部声明与旧「4 汉字」规则仍在），但**自本规范生效日起，与 L3 冲突的 08 旧规则一律以 L3 为准**；
   新修订只改 L3，禁止再改 08 正文（防双写漂移）。M8 后：08 与 docs 两份镜像**逐字一致**（`diff` 判据），
   且两者头部声明指向 L3——「三份文件一致」不可作为判据，因为 L3 与镜像的**范围本来就不同**（L3 是整体规范，镜像是子集）。
4. `nx_dev_skill` 的 `05-执行协议.md`（八条铁律 + 状态机）对**所有 NX 插件开发任务**无条件适用；本规范不重复也不削弱它。

### 2.3 适用与豁免

- **强制适用**：附录 A 全部插件仓 + `ikun_installer` + 两个知识库仓（仅镜像链义务）。
- **豁免登记（机器可判）**：任何「不适用」必须在仓库 `README.md` 写 `## 规范豁免` 标题 + 一行理由；
  `verify-repo.ps1`（M7b）检查该字段；无登记的豁免视为违规。
  现有豁免项：知识库两仓分支名为 `main`——**当前未登记，M2 补上**；除此之外再无豁免。
- **未登记仓死线**：`runner_section_area` 须在生效日起 30 天内「登记进附录 A 为独立插件」或「归档删除」；
  逾期未决按违规处理并在附录 A 标注。

## 3. 身份与命名（P1）

### 3.1 英文名「四同」

**仓库名 = 本地目录名 = 工程/dll 基名 = 插件 id**，四者逐字相同（继承 L2/08 §1.1）：

- 全小写 `snake_case`、纯 ASCII（`a-z 0-9 _`）、≤ 28 字符；
- 结构 `<对象>_<动作>` 或 `<对象>_<特征>`；
- 禁用 `nx_` 前缀、`test_/tmp_/new_/v2_` 临时前缀、产品编号/客户代号；
- **dll/dlx/dat 文件名必须等于仓库名**（`multi_entity_nester.dll`），菜单 `ACTIONS` 引用它。

### 3.2 中文名两级（修订 L2/08 §1.2）

原规则「全称正好 4 个汉字」与全部存量 `plugin.meta` 冲突（无一符合），**修订为**：

- **全称 `name_cn`**：≤ 8 个汉字，不带「爱坤」「工具箱」前缀，唯一、见名知义；
  允许「建模/CAM/PMI」等必要类别词，但不得与图标名相同造成混淆。
- **图标名 `icon_cn`**：≤ 2 个汉字。
- 现存 10 份 `plugin.meta` 的 `name_cn` 全部 ≤ 8 字，**无需改名**；仅需按附录 A 对齐个别不一致处。

### 3.3 命名债 `MultiEntityNester` → `multi_entity_nester`（唯一存量迁移）

分 4 个阶段，每阶段可独立提交、可验证、可回滚（详细清单见 §14 迁移项 M1）：

1. 仓内先行：源码/工程名改 `multi_entity_nester`，编译产出新名 dll/dlx（本地验证）；
2. 中心侧改引用：`plugins.json`、`custom.men`/`ikun.rtb` 的 `ACTIONS`/`BITMAP` 一并改（同一提交）；
3. Gitea 改名：仓库名改 `multi_entity_nester`（Gitea 自动重定向旧 URL，CI clone 用新名）；
4. 用户侧重装：发布一次里程碑 Release，说明「本版起排样插件更名，需重装」。

**禁止**：只改仓库名不动 dll（四同破坏）；只改 dll 不动菜单（V1 可用性破坏）。

## 4. 单一可信源（P2）

### 4.1 SSOT 矩阵（权威定义点唯一）

| 信息 | 唯一权威源 | 派生/消费方（禁止反向编辑） | 机器校验 |
|---|---|---|---|
| 插件英文名 | Gitea 仓库名 | 目录名、dll/dlx 基名、菜单 `ACTIONS`、图标文件名 `ikun_<名>.bmp` | 打包 gate G5 |
| 中文名/图标名/分类 | 插件仓 `plugin.meta` | Release 说明、菜单 `LABEL`、图标自动生成文字 | gate G5 |
| 是否并入爱坤 | `plugin.meta` 的 `in_ikun` | （登记表 plugins.json 只登记「是」的仓） | gate G5 |
| 并入登记（repo/ref） | `ikun_installer/plugins.json` | CI 收集清单 | gate G5 |
| 插件版本 | 插件仓 `CHANGELOG.md` 最新版本段头 | Release 增量说明 | gate G4 |
| 部署文件集 | 插件仓 `ikun-deploy.txt`（缺省 `*.dll *.dlx *.dat`） | CI 收集 | 打包时 |
| NX 菜单/ribbon 注册 | `DeployResources/startup/{custom.men, custom.tbr, ikun.rtb}` | NX 界面 | gate G7 编码 + G5 引用 |
| NX 开发知识/坑 | `nx_dev_skill` | `nx_dev_handbook`（镜像） | 人工（add-pitfall 协议） |
| 提交/分支/凭证规范 | `gitea-for-ai`（L1） | 全部仓库 | 人工 + 预提交自查 |

### 4.2 `plugin.meta` 字段规范（UTF-8、`key=value`、无 BOM）

```ini
name_cn=顶针布局          # 全称，≤8 汉字，唯一
icon_cn=顶针              # 图标名，≤2 汉字
category=建模             # 建模|CAM|PMI|制图|装配|钣金|其它
in_ikun=true              # true=并入爱坤；false=独立
```

- 四键**必须齐全**；新增字段必须先在本文档登记（防止两处定义同一信息）。
- **机器白名单**（G 系闸门与生成器共用，v1.0.1 勘误：存量 PMI 类拉丁图标名合法）：`icon_cn` 必须匹配 `^[\u4e00-\u9fff]{1,2}$|^[A-Z]{1,3}$`（1–2 汉字或 1–3 大写字母）；
  `name_cn` 仅汉字/字母数字、≤8 汉字、无控制字符；`category` 取枚举值。防 ImageMagick/菜单注入（§11.3）。
- `in_ikun` 是「该插件事实上的归属」，与 `plugins.json` 必须一致（gate G5）。

### 4.3 `plugins.json` 规范（改造项 M4）

- 条目简化为 `{ "repo": "<仓库名>", "ref": "master" }`；**删除 `icon` 字段**——图标文字由 CI 从该仓 `plugin.meta` 的 `icon_cn` 派生，消灭一处漂移。
- **追加式变更**：新插件一律追加到 `plugins.json` 与菜单/ribbon 文件**各自末尾**，禁止重排既有条目（重排制造无意义的 GBK diff 与审查噪音）。
  现状：`plugins.json` 顺序与 `custom.men` 顺序并不一致（历史形成），**不强制立即对齐**，此后按「各自末尾追加」演进即可；
  gate G5 只校验**集合一致**（§7.3），不校验顺序。
- `release_tag` 固定 `latest`。

## 5. 仓库结构标准（每个插件仓强制）

```
<plugin_name>/
  <plugin_name>.cpp / .hpp / .dlx    # 源码+界面（从 nx_dev_skill/templates 拷贝改写，禁止从零手写）
  build.ps1                          # 编译脚本（模板，机器判据：exit 0 产出 dll + dumpbin 双导出）
  plugin.meta                        # §4.2
  ikun-deploy.txt                    # 可选；每行一个 glob，禁止含 /（扁平部署 C2）
  README.md                          # What/Why/Run/Test 四段 + 「验收标准」小节（§10.1）
  CHANGELOG.md                       # §6 强制（并入爱坤的仓尤其强制）
  LICENSE                            # 统一 MIT（与仓库 license 字段一致）
  .gitignore                         # 必须覆盖 §7.4 禁止入库物 + .env/token
  .gitattributes                     # 行尾规则（*.sh/*.yml/*.yaml eol=lf；文本类统一 text）
  .gitea/workflows/notify-installer.yml  # 仅 in_ikun=true 的仓（统一模板，见 §8.2）
```

结构校验（机器可判，并入 CI 或本地脚本 `verify-repo.ps1`，迁移项 M7b）：
- **并入爱坤的仓（in_ikun=true）**：根目录必须存在上述清单全部条目（`ikun-deploy.txt` 与 notify workflow 按条件豁免）；
  缺任一即标黄，缺 `CHANGELOG.md`/`plugin.meta`/`LICENSE` **标红**；
- **未并入仓（in_ikun=false）与未登记仓**：结构清单**降级为提示**（标黄），但 `.gitignore` 覆盖禁止入库物（§7.4）、
  secret 扫描（G6）、`plugin.meta` 白名单（§4.2）三条**安全规则对所有仓同强度，无豁免**；
- 附录 A 清册由该脚本**扫描生成真值表**（对抗审查 P0-3：手工填表在 v0.1 就漂移了）。

## 6. 版本与变更记录（P4）

### 6.1 安装器版本模型

- 权威源：`ikun_installer.csproj` 的 `<Version>` = `MAJOR.MINOR.PATCH`；
- 完整版本 = `<Version>.<Gitea run_number>`（CI 注入，如 `2.1.0.54`）；
- **bump 规则**（人工，PR 里说明理由）：
  - `MAJOR`：安装器部署模型/UI 结构重构、不再兼容旧 NX 版本；
  - `MINOR`：新插件并入、新部署特性（如部署槽）；
  - `PATCH`：修复、菜单/图标调整。
- `run_number` 只增不减 → 版本号单调，更新器据此拒绝降级（§9.3）。
- **一切 UI 可见的版本字符串**（窗体标题、关于对话框、日志头）必须由程序集版本
  （`FileVersionInfo`）派生，禁止手写。现状违规：`Form1.cs` 标题手写 `v2.1`（见 §4.4）。

### 6.2 插件版本模型

- 权威源：`CHANGELOG.md` 的版本段头 `## vX.Y.Z (YYYY-MM-DD)`，三段式 semver；
- 允许顶部 `## Unreleased` 段累积日常条目；**每次更新制品（dll/dlx/dat）必须同步新增 CHANGELOG 条目**（gate G4）；
- 里程碑（并入新功能/季度/大改）时把 `Unreleased` 折叠为版本段：`## vX.Y.Z (YYYY-MM-DD)` 并 bump 版本号；
- 版本号单调递增；同一日期可多插件各自发版，互不影响。
- **Unreleased 上限（机器规则）**：顶部 `Unreleased` 段条目数 ≤ 20，超过在 G4 检查中一并标黄
  「Unreleased 堆积，应折叠为版本段」（现状 MultiEntityNester 已 40+ 条，属 M2 清理对象）；
  折叠动作为：新建 `## vX.Y.Z (YYYY-MM-DD)` 段并 bump 版本号。

### 6.3 CHANGELOG 格式（机器契约）

```markdown
## v1.2.0 (2026-08-07)

- **新增**: 导出后打开文件夹选项
- **修复**: 顶针卡死问题
```

- 版本段头严格 `## v?X.Y.Z (YYYY-MM-DD)`；
- 条目 `- **类型**: 说明`，类型 ∈ 新增/修复/优化/变更；
- 条目是发布说明的原材料：**写用户看得懂的话**，不写「改了代码」。

### 6.4 制品 ⇄ CHANGELOG 同步闸门（gate G4，渐进收紧）

- 阶段一（本规范生效起）：CI 对比上次基线，若某插件**制品变了但 CHANGELOG 无新增条目** → 发布说明中该插件标红
  「⚠ 本次更新无文字说明（违反 §6.2）」，并给该仓开 Issue；
- 阶段二（观察 ≥ 2 个发布周期后由维护者升级）：改为**打包失败**（P7 渐进收紧）。

### 6.5 安装器自身的 CHANGELOG

`ikun_installer` 同样维护 `CHANGELOG.md`（当前缺失，迁移项 M3），格式同 §6.3；
CI 发布说明新增「安装器更新内容」段（从该文件增量提取，复用现有 release-notes 函数）。

### 6.6 Release 名称契约（更新器解析依赖，机器契约）

- Release name 必须形如 `爱坤工具箱 v<X>.<Y>.<Z>.<W>`（`W` 可省）；
- `UpdateManager.ParseRemoteVersion` 从 name 提取版本 —— **改名即破坏更新检查**；
- 变更 name 格式必须同步改 `UpdateManager.cs` 并补单元测试（迁移项 M9）。

## 7. 构建与制品（P3、P5）

### 7.1 本地构建（开发机，唯一编译插件的地方，约束 C3）

- 用 `nx_dev_skill/templates/build.ps1` 模板（自动探测 VS + UGOPEN，无硬编码机器路径）；
- 机器判据：`build.ps1` exit 0 且产出 `<仓库名>.dll`；`dumpbin /exports <dll> | findstr ufusr` 必须看到
  `ufusr` 与 `ufusr_ask_unload` 两个导出（继承 L2 铁律 8）；
- 编译通过后先在 NX 里 Ctrl+U 加载冒烟（§10.4），再提交制品。

### 7.2 制品提交规则

- 制品（dll/dlx/dat）与**同一功能的源码改动在同一提交**提交；提交信息注明编译环境：
  `fix(xxx): ... \n\nBuilt: NX 1847 + VS2022 (v143)`；
- 禁止「先推源码、过几天补推 dll」——中间态的 notify 触发会打包出「新说明旧二进制」；
- 制品是普通 git 对象（非 LFS），保证 CI clone 可取（继承 L2/08 §3）。

### 7.3 CI 制品校验闸门（G1–G8，全部机器可判、无需 NX，改造项 M7 实现）

> **边界声明（对抗审查结论）**：G1–G8 是**完整性/一致性闸门**，**不做行为/恶意性判定**——
> 它们拦得住「名字错了、XML 坏了、缺导出、没写说明」，拦不住「dll 里跑什么代码」。
> 恶意代码的拦截依赖三道补充防线：① 制品变更强制 PR + §13 D 类红队审查（§12.3）；
> ② G8 源码-制品绑定（可机器证伪）；③ M13 安装器代码签名（fail-closed）。三者缺一，信任链不闭合。

打包前逐项检查，任一标红即**打包失败**（G4 除外）：

| Gate | 检查 | 判据 |
|---|---|---|
| G1 | 每个在册插件至少收集到 1 个文件 | assemble.sh 已有「未匹配到部署文件」→ 升级为失败 |
| G2 | 每个 `.dlx` 是合法 XML（UTF-8 解析） | 沿用 build.ps1 的校验逻辑搬到 CI |
| G3 | 每个 `.dll` 的 PE 导出表含 `ufusr` 和 `ufusr_ask_unload`（已实测：现存 17 个 dll 全部真实导出，G3 对存量成立） | 容器内 `llvm-objdump -p`/`objdump` 或 python pefile——**`dotnet/sdk:9.0` 基础镜像不含这些工具，M7b 须在 pack 工作流安装（固定版本）** |
| G4 | 制品变化 ⇄ CHANGELOG 新条目（§6.4；**开 Issue 一律开在 ikun_installer 仓**并标注插件名——避免 CI token 需要各插件仓写权限，与 M11 最小权限一致） | 阶段一警告，阶段二失败 |
| G5 | 一致性（**双向**）：`plugins.json` == 全部 `in_ikun=true` 的仓（双向由 verify-repo.ps1 扫描 `registry.json` 判定——它 clone 全量清册仓读 meta；pack 内只查 plugins.json 方向 + 菜单集合，数据源分工避免重复 clone）；菜单 `ACTIONS` 集合 == 在册 dll 集合 + `ikun_updater.dll`（口径=application/ 实际 dll 基名集合）；**收集结果每仓 dll 基名唯一且 == 仓库名**（防 M1 改名期双 dll 同收）；菜单 `BITMAP` 文件名 == `ikun_<英文名>.bmp` 且 startup/ 无孤儿/重复 bmp；`LABEL`/`BITMAP` 引用都存在；菜单 `LABEL` 非空、互不重复、GBK 解码后无乱码；**菜单 `LABEL` == 该插件 `plugin.meta.name_cn`（字节比较，GBK 解码后）** | 静态比对（`registry.json` = 附录 A 的机器形态，由 verify-repo.ps1 扫描生成、存放于 L3 仓；LABEL 对齐任务见 M8b） |
| G6 | 禁止入库物：`.obj .pdb .exp .lib .ilk .sdf` 等（§7.4）不出现在收集结果与仓库树；**并扫描本次提交 diff 的 secret**（`glpat-`、`ghp_`、`Authorization: token`、长度 ≥32 的 hex/base64 疑似串） | 静态扫描（secret 扫描覆盖 §11.1 的机器执法缺口） |
| G7 | 菜单文件 GBK 解码→再编码**字节往返一致**且无 U+FFFD，**并与 G5 的 LABEL==name_cn 比对联动**（UTF-8 误存会让中文字节被当 GBK 解成「鐖卞潳」类合法字符而非 U+FFFD——单靠替换符检查抓不住，必须靠文本比对兜底）；**NX 菜单结构合法**：BUTTON 块 LABEL/BITMAP/ACTIONS 齐备、MENU/END_OF_MENU 配对（NX 菜单方言勘误 v1.0.1）、`ACTIONS` 目标存在、`LABEL`/`BITMAP` 引用无悬空、`VERSION` 合法 | `iconv -f GBK -t UTF-8` 往返 + 替换符检查 + 固定解析器做块配对（防「编码对、结构碎」的坏菜单砸掉整个菜单） |
| G8 | **源码-制品绑定**（迁移项 M14，渐进：新提交制品强制、存量宽限一个周期）：dll 版本资源/常量内嵌构建时 `git rev-parse HEAD` 短 SHA，CI 用 `strings`/`llvm-objdump` 提取并与该仓 HEAD 比对 | 提取不到或不等 → 标红（「这份 dll 声称由这份源码编译」的最强机器可判代理；`ikun_updater.dll` 同样纳入） |

### 7.4 禁止入库物清单（继承 + 补充）

`*.obj *.exp *.lib *.ilk *.pdb *.pch *.sdf *.suo *.user *.aps *.winmd *.winmdpdb`、
`bin/ obj/ publish/ ref/ refint/`、`.env *.token secrets/`。
现有违规：`runner_section_area/runner_section_area.obj`（迁移项 M2 清理）。

## 8. 注册与接入爱坤（V4 可演进的确定性路径）

### 8.1 强制问询（继承 L2/08 §7，保留）

创建/初始化任何新 NX 插件工程时，**必须先问用户**「是否并入爱坤工具箱」。答「是」走 §8.2；答「否」仅建仓并在
`plugin.meta` 写 `in_ikun=false`；无论并入与否，**都必须登记进附录 A 清册**（提交 PR 到本规范所在仓）。

### 8.2 三步接入（每步同一提交完成，禁止半成品）

1. **登记**：`ikun_installer/plugins.json` 加 `{ "repo": "<名>", "ref": "master" }`；
2. **界面**：`DeployResources/startup/` 三个文件各**追加**一条 BUTTON 块到末尾：
   `custom.men`（菜单，`ACTIONS <名>.dll`，**LABEL 文本逐字等于该仓 `plugin.meta` 的 `name_cn`**）、
   `ikun.rtb`（Ribbon，分组按 category）、`custom.tbr`（工具栏，可选）；
   **必须用 GBK 编码工具读写（Encoding 936 / iconv）**；图标 bmp 可缺省（CI 自动生成，文件名 `ikun_<名>.bmp`）；
3. **通知**：插件仓加 `.gitea/workflows/notify-installer.yml`，从**唯一权威模板**
   `ikun_installer/docs/templates/notify-installer.yml`（迁移项 M7b 建立）复制；
   **允许的唯一定制 = `on.push.paths` 列表**（按本仓制品扩展名，如含 `.def` 的插件把 `**.dat` 换 `**.def`），
   且必须在文件头注释注明「模板: <路径>, 定制: paths=<扩展名>」；
   dispatch 端点、secret 名、分支名**禁止改动**。现状 7 份副本中 6 份相同、1 份合法定制（plate_dwg_export 用 `.def`），
   本规则把该定制模式固化为唯一允许形态。

### 8.3 接入后的机器验收（接入者必做，否则视为未完成）

- 触发一次该仓 push（制品变更），确认 `ikun_installer` 的 `pack-installer` 运行成功；
- 确认 Release「子项目更新内容」出现本插件条目；
- 本机下载 exe 安装，在 NX 菜单/ribbon 看到按钮，点击弹出对话框。

## 9. 发布与更新（V2 可达）

### 9.1 发布轨道（规则化现状）

| 轨道 | 用途 | 规则 |
|---|---|---|
| **滚动 `latest`** | 日常唯一通道，更新器检查目标 | 每次 pack 删除重建、tag 指向当前 HEAD、只含 `ikun_installer.exe` 一个资产、正文内嵌 `<!-- ikun-plugin-revisions:... -->` 基线（现有机制保留，是增量说明的可靠基线） |
| **里程碑 Release**（`vX.Y.Z`） | 冻结存档：大版本、改名、需要全员重装时 | 从当时 `latest` 的产物复制创建；创建后**永不再动**；正文注明「快照自 latest @ <run_number>」 |

禁止：给旧里程碑 tag 推新构建；在 `latest` 之外再开第二个滚动轨道。

### 9.2 发布说明生成（现有机制 + 扩展）

- 子项目增量：现有 `assemble.sh`/`release-notes.sh` 机制（基线 diff + CHANGELOG 提取 + 消毒 + 每插件 ≤8 条）保留；
- 新增「安装器更新内容」段（§6.5）；
- 每次 Release 正文最后附 sha256（增强项 M10，落地后更新器校验）。

### 9.3 更新链契约（UpdateManager / ikun_updater 必须满足）

1. 远端版本 = Release name 提取（§6.6 契约，正则须带锚点且 ≤4 段）；本地版本 = FileVersion；
2. **版本只增不减**：远端 ≤ 本地时不提示、不下载（防降级/重放）；
3. **下载与校验 fail-closed**（对抗审查 P0-3 修正）：
   - 下载走 https + 系统证书校验，下载到 `%LOCALAPPDATA%` 用户级目录（禁止 `%TEMP%` 共享目录，
     防同机低权限用户 TOCTOU 换文件）；
   - **签名缺失或无效 → 拒绝执行**（M13 落地前先拒绝对「无签名却放行」的现状，M13 后以 Authenticode 为准）；
   - 「FileVersion == 远端版本」只作**防损坏**检查，不得当作防伪造凭据；
   - 校验通过后以独占方式重新打开并持句柄执行，收敛校验-启动窗口；
4. 代理默认值（`192.168.1.5:6666`）等环境差异必须走注册表/配置，禁止硬编码进新代码（迁移项 M6 清理现有）；
5. **自签 CA 带外分发是更新链的前置条件**：必须按 §11.6 把自签 CA 预置进用户系统信任库并写入安装文档；
   未预置 CA 时更新检查会静默失败——安装器须检测并给用户可见提示，禁止静默。
6. M10 落地后：下载后校验 sha256（与 Release 正文比对，失败拒绝安装）；**定位为第二道完整性校验**，
   不替代签名——sha256 与资产同在 Gitea，攻击者能改资产就能改正文（同信道局限）。

### 9.4 回滚策略

- 不提供自动降级（与 9.3.2 一致）；出问题的版本处理路径 = **向前修复**：修好后推制品 → 自动打包 → 用户重装新 exe；
- 紧急止血时允许临时从 `plugins.json` 移除某插件重新打包（提交注明原因，事后恢复）。

## 10. 质量与测试（P5）

### 10.1 子项目验收标准

每个插件 `README.md` 的 Test 段必须写**用户可执行的验收标准**（模板：打开对话框 → 输入什么 → 点应用 →
在部件导航器/图形区看到什么）。这是 L2 需求确认卡第 7 条的固化产物。

## 11. 安全与凭证

1. **Token 红线**（继承 L1 §8）：GITEA_TOKEN 等不得写入任何文件；`.env`/`*.token` 必须在 `.gitignore`；
   本规范作者从用户处获得的凭证仅用于本次会话的 Gitea API 访问，不落盘。
2. **CI 凭证最小化（对抗审查修正）**：现况的 `INSTALLER_DISPATCH_TOKEN` 实际是**跨仓读 + 安装器 release/tag/资产写的万能 PAT**，
   在 7 个插件仓各存一份——泄露爆炸半径 = 直接覆盖 `latest` 资产。本规范要求（迁移项 M11）：
   ① 拆成两个 token：`INSTALLER_DISPATCH_TOKEN`（仅 dispatch 权限，放插件仓）与 `INSTALLER_RELEASE_TOKEN`
   （仅安装器仓 release/tag 写，只存在于安装器仓）；
   ② 全部 token 设过期时间并定期轮换；
   ③ CI 前置步骤用 `/api/v1/user` 自测当前 token 实际 scope，发现「release 写」即告警；
   ④ `notify-installer.yml` 模板**禁止 `curl -k`**，改由 runner 信任自签 CA（与 §11.6 证书策略一致）。
3. **制品消毒与外部输入白名单**：Release 正文对 CHANGELOG/commit 标题的 sanitize（去 URL/邮箱/HTML）已实现，任何改动不得削弱；
   并扩展到**一切进入 shell 脚本/ImageMagick/菜单生成器的 `plugin.meta` 字段**：
   - `icon_cn` 机器白名单 `^[\u4e00-\u9fff]{1,2}$|^[A-Z]{1,3}$`（1–2 汉字或 1–3 大写字母；v1.0.1 勘误）——防 `@file` 读文件与 `%` 转义
     （ImageMagick `-annotate` 注入，CVE-2016-3714 同类，可把 CI 环境变量渲染进公开图标）；
   - `name_cn` 白名单（汉字/字母数字，≤8 汉字，无控制字符）；`category` 枚举值；
   - 未来若由 meta 自动生成菜单 `LABEL`，生成器必须做菜单语法转义（防注入 `BUTTON/ACTIONS/END_OF_MENU` 块）；
   - Release 正文中的 `repo` 名白名单 `^[a-z0-9_]+$`。
   新增 sanitize/白名单规则必须先过对抗审查。
4. **禁止硬编码**：机器路径、代理、端口一律环境变量/注册表/配置。现状已核验 **6 处**违规，全部按迁移项 M6 处置：
   ① `build.ps1`（`Y:\...`、`E:\NX二次开发\项目`）② `update.ps1`（`D:\Program Files\ikun tools`、`E:\...`）
   ③ `Form1.cs` 的 `IkToolDir`（安装目录）④ `nxplugin/ikun_updater.cpp` 的 `IKUN_EXE`
   （**编译进 dll**，改动需重编 nxplugin 并与安装器支持自定义目录同步落地）
   ⑤ `UpdateManager.cs` 的 `DefaultProxy`/`GiteaLatestApi`（默认代理与 API 地址必须注册表/环境变量可覆盖）
   ⑥ `DeploymentLayout.cs:62` 的 `E:\NX二次开发\项目\nx_tools_deploy`（legacy 标记路径）。
5. **菜单文件视为敏感文件**：改 `custom.men`/`*.rtb`/`*.tbr` 必须走 PR + gate G7（编码守卫 + 结构校验），
   合并前人工核对 diff 无乱码（GBK diff 显示为 UTF-8 预览）。
6. **证书策略**：自签 Gitea 的信任方式是「把自签 CA 安装进 runner/用户系统信任链」；
   `curl -k`、`git -c http.sslVerify=false` 一律降级为「仅一次性诊断手段」，禁止写进任何常驻工作流/文档默认方案
   （现状违规：7 份 notify-installer.yml 的 `curl -k`，随 M11 一并整改）。
7. **安装器自身危险操作红线**：下载文件必须落用户级受保护目录（`%LOCALAPPDATA%`，禁止 `%TEMP%` 共享目录）；
   以管理员运行下载的 exe 前必须 fail-closed 校验（签名/哈希，见 §9.3）；禁止以管理员写非白名单目录；
   校验与启动之间的 TOCTOU 窗口必须靠「校验通过后独占打开 + 校验句柄」收敛（§9.3.3）。

## 12. 协作流程

### 12.1 提交规范

引用 L1（gitea-for-ai）：Conventional Commits（feat/fix/refactor/docs/chore，可加 scope）+
trailers（Co-Authored-By / Agent / Device）+ 提交前 5 项安全检查。本规范追加两条：

- 触及 `plugins.json`/菜单文件/CHANGELOG 的提交，scope 统一写 `ikun`，如 `feat(ikun): 接入板面导出插件`；
- **禁止 force push 到任何默认分支**——M12（分支保护）生效当日完成前该条为自律红线，之后由 Gitea 强制；
- **提交签名（渐进目标）**：默认分支合入提交逐步启用 GPG/SSH 签名（现状全部 `not_signed`）；M12 落地后的下一里程碑，
  中心仓开启「要求签名」状态检查。

### 12.2 分支策略

- 插件仓与 `ikun_installer`：默认分支 `master`；≥3 commits 的大功能开 `feat/<name>` 分支，合完即删；
- 知识库两仓：默认分支 `main`（**豁免须在 README 登记**，§2.3），其余规则同上；
- 分支保护：全部生态仓默认分支开保护（禁 force push，M12 生效当日完成）；PR 流程后加「至少 1 个审查人」。

### 12.3 PR 与审查

- 单人开发时允许直接提交 master；以下**五类**变更**必须开 PR**（合并前过 §13 对抗审查）：
  1. 新插件接入（§8.2 三步）；
  2. 插件改名/仓库改名（§3.3）；
  3. `plugins.json`/菜单/ribbon 结构性变更；
  4. **制品变更（push 任何 dll/dlx/dat，§7.3 边界声明的第一道防线）**：制品+源码先合入
     `feat/<name>` 分支 → PR → D 类审查（机器清单，首次接入为人工红队）→ 合并 master 后才触发打包；
     单人开发允许自合并，但审查记录必须归档（§13.4）；
  5. 本规范（L3）的任何修订。

## 13. 对抗性审查制度（P8）★

> 目的：规范、发布物、重大变更在「出厂」前被独立的攻击性视角检验。
> 审查者不是「挑错」，而是**试图让这个变更在真实环境里失败**。

### 13.1 触发条件（对抗审查落地性修正：按「风险 × 可逆性」分级，防自审表演）

| 审查对象 | 时机 | 输出 |
|---|---|---|
| A 规范修订 | **仅 v1.0/v2.0 级语义变更**（结构、闸门、SSOT 矩阵、信任链变更）；措辞修正/勘误不触发全量红队 | 审查报告（附录 D 模板）+ 修订记录 |
| B 重大架构变更 | 部署模型/更新链/CI 闸门/SSOT 矩阵变更 | 同上 |
| C 发布制品 | 每个里程碑 Release（人工红队，审 Release 正文+结构）；滚动 latest 不做人工抽查，改为 **pack 失败自动归因**（CI 日志 + Issue） | 抽查报告 / 归因记录 |
| D 新插件接入 | PR 合并前：**以机器 checklist（附录 B 逐项退出码/dumpbin/GBK/gate 校验）替代人工红队**；人工红队仅保留**首次接入**（沉淀为机器清单后不再人工） | 机器清单输出 + 首次红队报告 |

### 13.2 角色与独立性

- **红队**：与变更作者不同的 AI 会话/模型（或另一位真人）；同一会话自我审查不算数；
- 红队拿到的是：变更 diff + 设计说明 + 本规范 + 附录 A 清册，**不参与实现**；
- 红队结论分三级：**P0 阻断**（可导致不可用/数据损坏/安全事件/规范自相矛盾）/
  **P1 必须修**（明显缺陷、规则漏洞、可预期的返工）/ **P2 建议**（优化、文档、边界情况）。

### 13.3 攻击面清单（红队必打的角度）

| 角度 | 攻击问题示例 |
|---|---|
| 一致性 | 两条规则对同一场景给出矛盾指令吗？SSOT 矩阵有循环派生吗？镜像链会断吗？ |
| 可用性 | 按规则做，NX 里真能看到/加载吗？GBK/UTF-8 会打架吗？菜单引用会悬空吗？ |
| 安全 | 恶意子项目能不能污染 Release 正文/菜单/图标（含 `plugin.meta` 字段 → ImageMagick/菜单生成器的注入）？token 最小权限是否成立？更新链能否被降级/替换/本地 TOCTOU 提权？ |
| 落地性 | 规则机器可判吗？第一天执行会不会卡死正常开发？迁移计划顺序对吗（先改谁后改谁才不会断裂）？ |
| 边界 | 新插件、改名插件、未并入插件、孤儿仓库、Python 插件（single_line_text）——规则是否全覆盖？ |
| 退化 | 有没有规则会让已装用户的老安装无声坏掉？有没有规则依赖「所有人都记得」？ |

### 13.4 结论处置

- 存在未闭环的 P0 → 禁止合并/发布；P1 → 修完再合或登记豁免理由；
- P2 → 记录进文档「已知遗留」清单，下个里程碑处理；
- 审查报告与整改记录**同变更一起提交**（放 `docs/adversarial-review/` 或 PR 描述），保证可回溯。

### 13.5 本规范的对抗审查安排

本文档 v0.1 已通过三轮红队攻击（一致性/安全/落地性），三份报告与整改记录归档于
`docs/adversarial-review/`（与本文档同仓），全部 P0 闭环后升 v1.0；
此后**语义级**修订按 §13.1 的 A 类执行，勘误级修订走普通 PR。
